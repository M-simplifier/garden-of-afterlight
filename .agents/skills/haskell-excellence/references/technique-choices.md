# 技法の選び方

型、実行時検査、PBTは異なる誤りを扱う。使う技法を増やすことを目標にしない。

## 値と不変条件

| 必要な区別 | 候補 | 判断の要点 |
| --- | --- | --- |
| 同じ表現でも混同してはいけない値 | `newtype` | 数値や文字列の置換で、意味の違う引数を渡せなくなるか |
| 有効な状態の組合せが限られる | sum/productのADT | 互いに矛盾する複数のフラグより、可能な状態を直接表す |
| 一部の表現値だけが有効 | smart constructor、非公開constructor | 作成だけでなく更新・decode・公開インスタンスにも迂回路がないか |
| 実行時の失敗理由で対処が変わる | `Either DomainError a` | 表示用の文章への変換を境界まで遅らせる |
| 不在そのものが結果である | `Maybe a` | 呼び出し側が理由を必要とする失敗まで隠さない |
| 空でないことが操作の前提 | `NonEmpty`、専用型 | 呼び出すたびに `head` の前提を推測しなくて済むか |

非負量のwrapperでも、公開constructor、無制約の `Num`、生値を通す `Read` から
負値を作れれば保証は崩れる。観測・更新・decodeを含むAPI全体で不変条件を保つ。
入力の構文エラーと意味上の拒否を区別する。
独立した複数の入力エラーを一度に返す要件なら、検証結果を蓄積する設計を選ぶ。
通常の `Either` の逐次処理は最初の失敗で止まる。

## 型で操作を制約する

- **phantom type / typestate**: 未検証と検証済み、開いたhandleと閉じたhandle等、
  静的に区別できる段階の取り違えに使う。constructorを隠すだけで十分とは限らない。
  phantom parameterのroleにより `coerce` で制約を迂回できるなら、nominal role等を検討する。
  同じhandleの別名から状態が変わる問題や、外部システムの実状態は別途扱う。
- **GADT**: constructorごとに戻り値の型や利用できる証拠が変わる場合に使う。
  型付き式、コマンドとその結果の対応などが候補。単なる選択肢には通常のADTで足りる。
- **DataKinds / type family**: 閉じた状態集合や、入力型に応じた結果型がAPIを支える場合に使う。
  普通の型引数で表せるものを型計算へ移さない。動的な値には境界で検査し、
  存在型等で証拠と操作をまとめる選択肢がある。
- **existential / rank-n**: 実行時に選ばれる異種の実装を隠す、抽象表現の流出を制約する、
  多相なcallbackを受け取る場合に使う。sum型や関数のレコードで十分か比較する。
  rank-nの形だけで外部資源の解放や遅延値の安全まで保証したと考えない。
- **linear type / refinement**: 使用回数や局所的な数値・長さの関係が特に重要で、
  現行toolchainで維持できる場合に検討する。証明した性質と、FFI・例外・外部入力など
  検証対象外の境界を明確にし、実行検査も残す。

型エラーや利用側の証拠構築まで含めて判断する。頻繁に変わる動的ルールは、
純粋な判定関数と検査の方が適することもある。

## 合成と抽象化

`Functor` は構造を保つ写像、`Applicative` は前の結果に依存しない計算の組合せ、
`Monad` は前の結果によって次の計算を選ぶときに使う。
必要のない `Monad` 制約を加えない。一方、`Applicative` の使用だけで並列実行や
エラー蓄積が得られるわけではなく、それは選んだ型とインスタンスの意味による。

独自の型クラスは、安定した操作と法則、多相的な利用が役立つ場合に使う。
通常の関数や依存関数のレコードと比較し、最小定義・法則・使用例を残す。

`Semigroup` の結合則や `Monoid` の単位元則に加え、ドメインとの対応も確認する。
「先の変更 `a` と後の変更 `b` を合成する」なら、たとえば
`apply (a <> b) s == apply b (apply a s)` がその対応を表す。
合成が結合的でも、順序を交換できるとは限らない。
`Eq`・`Ord`・数値などの導出は、その表現で必要な法則が成立するか確かめる。

| 実際にある構造 | 候補と制限 |
| --- | --- |
| 深く入れ子になった不変データの更新を繰り返し合成する | optics。浅い数個のrecord更新なら直接書く。公開するopticも不変条件を保つ必要がある |
| 同じ再帰形に多数の解釈・変換がある | recursion schemes。単純な再帰1本を抽象化する理由にはしない |
| 入力と出力を別々に変換して合成する | profunctor等。型の形だけで選ばず、利用側の変換を確かめる |
| 静的な接続構造を持つ計算を組み立てる | Arrow等。通常の関数合成やApplicativeとの違いが必要な場面で使う |
| 注目点の周囲の文脈から局所結果を計算する | zipper / comonad等。文脈を渡す普通の関数よりモデルが明瞭になる場合に使う |

## 効果と資源

まず純粋な計算と実際のIOを分け、境界の依存を引数やレコードで渡す。
共有設定やサービスが増えたアプリケーションでは `ReaderT Env IO` も候補になる。
巨大な可変状態を `Env` へ集めることとは区別する。
既存プロジェクトの `mtl` や効果系は、局所的な能力と実行方法が読める範囲で利用する。

- **final tagless**: 安定した操作の集合を、複数の解釈・翻訳・最適化で使う場合。
  型クラス化しても、解釈を分ける価値がなければ通常の関数でよい。
- **free / freer**: 計算の手順をデータとして観察・変換・再解釈することが必要な場合。
  依存注入だけなら、より小さな境界から始める。
- **algebraic effects**: 効果の組合せやhandlerの入替えが設計上の問題を解く場合。
  解放・例外・キャンセルの意味は採用した仕組みで別途確認する。

取得・使用・解放は `bracket` や同等の資源管理へまとめる。
単に `finally` を後置しても、取得直後の例外が解放登録前に届く隙間を防げるとは限らない。
非同期例外を長時間maskしてキャンセル不能にする修正や、広い `catch` による
キャンセルの握り潰しを避ける。子処理は親の寿命と終了経路に結びつけ、
共有状態の操作を複数に分ける場合は、その途中状態と原子性を検討する。

## 遅延評価と空間使用量

計算量、不要な再走査、長寿命の値が保持するデータを先に確認する。
蓄積する計算が原因ならstrictなfieldや `foldl'` を検討するが、いずれも通常はWHNFまでで、
入れ子の中まで評価するとは限らない。`Map.Strict` 等の名前だけで深い評価を仮定しない。
反対に、一律のstrict化は不要な計算を実行し、停止性や例外が起こる時点を変えうる。

データ構造は検索・走査・更新の頻度とサイズから選ぶ。
遅延IOやstreamを使う場合は、値を消費し終えるまで資源が生存するか確認する。
測定では構築だけでなく、利用側が実際に必要とする程度まで結果を評価する。
CPU時間だけでなく、割当量や生存メモリも症状に合わせて調べる。
