# 検証とレビュー

変更が壊しうる性質に合わせて検査を選ぶ。全項目の一律実行は必要ない。

## 検証の選択

| 変えたもの | 確かめること |
| --- | --- |
| 型・公開API・インスタンス | 影響するcomponentと呼び出し側の型検査。排除する誤用が重要なら拒否例も検査 |
| 純粋な規則・変換 | 代表例、境界例、法則、仕様から作った独立モデルとの比較 |
| 検証・codec | 正常系の往復、壊れた入力の拒否、境界値、互換性が必要なら固定fixture |
| 状態を持つ処理・protocol | 入力列、失敗前後の状態、遷移の前提、簡単な参照モデルとの一致 |
| 資源・並行処理 | 成功・失敗・キャンセル時の解放、子処理の終了、実際の境界との接続 |
| 性能に関わる表現・評価方法 | 現実の利用に合う入力と評価範囲で、時間・割当・生存メモリを比較 |

`cabal build` と `cabal test` だけで全ての実行検査を網羅するとは限らない。
CI、検査用executable・script、別componentの利用例も確認する。
formatterやlintは意味の検査の代用にしない。

## 型と全域性

網羅性の警告と、`head`・`fromJust`・`read`・未検査の添字等の到達経路を見る。
呼び出し側の慣習に頼る前提は、型か分岐へ移す。必要なunsafe/FFI処理は、
小さな境界に閉じ込め、その前提を呼び出し側まで確認する。
公開更新・導出インスタンス・`coerce`・decodeが不変条件を迂回できないかも調べる。
型で禁止する操作の負例は、本来の制約で拒否されたことを確認する。
importミスや依存欠落による非ゼロ終了は、その根拠にならない。
Haskellの型検査や網羅性検査は、停止性や全入力での例外不在の証明ではない。

## 意味のあるプロパティ

実装とは独立に法則と前提を書く。結合則・単位元、正規化の冪等性、保存量、順序、
無関係な入力への不変性、最適化前後の同値など、意味がある関係を選ぶ。

往復則 `decode (encode x) == Right x` では、正規化や一時情報の除外が仕様にあるか確認する。
比較を通すために都合の悪い差を消さない。encoderとdecoderが同じ誤りを共有しても
往復則は通るため、外部形式の期待、互換性fixture、無効入力の検査で補う。

- 有効値は可能なら構成で作る。大量のfilterで、調べたい入力をほとんど捨てない。
- 拒否すべき値は別に生成し、範囲外・不足・上限付近・空入力を意図して含める。
- 縮小後もプロパティの前提を保つ。必要な入力分類が出たかcoverageも確認する。
- 反例は小さな再現例として残し、乱数seedだけに依存しない。

単純な参照モデルと、本番の呼び出し経路を比較する。
式の写し、定数結果でも通る検査、前提が一度も成立しない含意では弱い。
重要な性質では、小さな誤変更を検出できるかを見ることも役立つ。

## 効果の境界

`SomeException` 等の広い捕捉がキャンセルを正常値や再試行へ変えていないか、
timeout後に子処理や資源が残らないかを見る。ドメインの拒否とIO障害の原因を区別する。
mockだけで終えず、変更したファイル・handle・FFI等の実際の利用で
取得・解放・失敗・終了を確かめる。純粋モデルの外に残る責任を明示する。

## 差分を読む観点

- エラー処理が呼び出し側へ文字列解析や部分関数を要求しないか。
- 新しい抽象化に利用例があり、制約・依存・言語拡張の費用が見合うか。
- インスタンスの法則と、合成順序等の操作の意味が両方合っているか。
- closureやcollectionが不要なデータを保持しないか。測定では結果を必要な深さまで評価したか。
- 実際の利用経路で、変更した動作、互換性、終了を確認できたか。

レビューでは入力・到達経路・壊れる性質を示し、高度な技法への置換や書式の好みを不具合扱いしない。
