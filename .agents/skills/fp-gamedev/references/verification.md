# 検証と保証の境界

[Haskell側の品質基準](../../haskell-excellence/SKILL.md)に加え、
ゲームでは状態の連なりと実際の入出力を検査する。

| 根拠 | 確認できること | それだけでは言えないこと |
| --- | --- | --- |
| 型・非公開constructor | APIで表せない矛盾 | 全入力での停止、全ルールの正しさ |
| 境界の検証 | 受理時の制約 | 後続遷移でも制約が閉じること |
| 例・PBT・モデル比較 | 調べた範囲の反例不在 | 任意長・任意入力の証明 |
| 本番入力を通るシナリオ | 到達・進行・再開 | デバイス入力や操作感 |
| 実機・展開後の起動 | 対象環境での観測 | 全機種での動作や楽しさ |
| 形式証明 | 明記した意味論と仮定の性質 | 別実装・FFI・描画への自動的な保証 |

## 法則から検査を選ぶ

- **遷移**: 不変条件、資源の保存、合法な進行、同じ入力列の再現。
- **合成**: 変更の結合・単位、入力列の分割と連結、batchの順序契約。
- **保存**: 永続化対象の往復、旧版fixture、破損拒否、再開直後の表示と効果。
- **キャッシュ**: 毎回作り直す参照と増分版の一致、削除と同tickの複数編集。
- **空間**: 座標変換、独立に定めた左右、衝突境界、視覚と意味の一致。
- **時間**: 押下の保持・一回性、期限境界、キャンセル、ポーズ、catch-up。

期待値を同じ実装式から作らず、小さい独立モデルや仕様由来の具体例を使う。
有効状態は有効に生成し、shrinkingでも必要な前提を保つ。不正入力は別の拒否検査にする。
単発操作だけで届かない状態にはモデル／状態機械と長いtraceを使う。
分類・coverageで必要な分岐へ届いたことを確認し、見つかった反例は最小回帰例として残す。

自動プレイは本番の入力変換と遷移を通す。ゴール状態への直接書き換えを
「そのルートを遊べた」根拠にしない。検査対象の入力列・条件と、未確認の範囲を残す。
例: [GardenCheckとTour](afterlight.md)。

## 証明・共通化へ進む場合

純粋Haskellにもbottom、部分関数、遅延評価、浮動小数、ライブラリの意味が残る。
証明対象は全域的で小さい境界に取り、仮定を型やデータとして明示する。
別言語に書き直したモデルの証明と、実行されるゲームの証明を区別する。
抽出した実行核、または実装との対応を証明して初めてその隔たりを閉じられる。

型付きDSLや共通エンジンは、異なるゲームで同じ法則が必要になったときに検討する。
共通するrecordの形だけでは抽出理由にならない。具体的な用途、共通法則、
ゲーム固有の意味、合わない反例を確かめる。命令をデータとして表すと、
本番・trace・モデル検査などの複数解釈へ意味を共有しやすい。
衝突・浮動小数・livenessには離散ルールと別の証明条件が必要。
