# 性能と意味の保存

## 重い場所を切り分ける

同じbuild・解像度・入力route・初期世界・warmupで比較する。
平均FPSに加え、遅いframeの分位と最大値、更新tick数、捨てた時間、allocation/GCを見る。
simulation、形状再生成、native転送、draw発行、present待ちを分ける。
draw前後の実時計はGPU時間ではない。区別が必要なら対象OSのprofilerを使う。
計測状態とDebug表示をゲームの正本・save・replayへ混ぜない。

大量破壊なら「何個表示したか」だけでなく、実際に動いた物体、接触、支持の喪失、
形状更新、完走、最大メモリを確認する。小さい局所破壊の結果を全崩壊へ拡大しない。
自動routeは通常入力と同じ意味経路を通し、目標の負荷状態へ到達したことを検査する。

## 最適化の選択

| 観測した負荷 | 検討する変更 | 守るもの |
| --- | --- | --- |
| 不変データの再導出 | 版付きcache、事前計算 | fresh derivationとの一致 |
| 大量のboxed値・GC | strictness、適切な配列、局所`ST` | 外へ可変状態を漏らさないAPI |
| 全世界・全pairの走査 | sparse chunk、空間索引、active work | 候補を取り落とさないこと |
| 同じ形状の再生成・転送 | mesh共有、instance化、native view | material・lighting・寿命の一致 |
| 一frameにcatch-upが集中 | 確定済みtick入力のqueue | 順序・edge・移動量・時間の保持 |

queueには容量と追いつけない場合の方針を持たせる。高い描画頻度を前提に一tickずつ
処理する方式は、持続的な過負荷の解決にはならない。
ECS、並列化、SIMDは実測した支配要因に対して選び、純粋な参照と同じ仕事で比較する。
workerや格納順は安定した意味上のIDと分ける。

巨大な不変base＋編集履歴では、baseの検証を再利用し変更分だけ検証できる。
ただし更新の一部が履歴を通らないと不正な差分を受理する。全更新を通す境界を設け、
独立した全復元と、本番の変更列で一致を確認する。

## 大量ボクセル・拘束解法

採用する精度を先に定める。塊への集約、sleep、装飾破片化、物体数上限は、
完全な剛体群と同じ法則とは限らない。許された近似として設計するか、同値性を示す。
占有、支持成分、衝突索引、可視面には同じ編集batchを反映し、
純粋核と別の正本を最適化側に作らない。

支持成分やbody生成はID・成分順・要素順まで必要な正準順を定める。
広域探索のfallbackも同じ結果を返す。接触manifold、warm start、sleep/wake、
同tickのdamage/eventは法則の一部。単一接触点やsolver順の変更を単なる高速化と扱わない。

ビット単位の一致が要件なら、operatorと数値演算順を固定した遅い参照を残す。
完全な値と浮動小数のbitsで、fault・接触履歴・event・順序まで差分検査する。
hash一致だけを同値性の証明にしない。worker数の変更でも同じ条件を検査する。

## 継続的なnative evaluatorを使う場合

まず純粋な参照と局所`ST`で境界を確立する。永続arenaやFFIを採る場合は、
意味上の状態と実行用storageを分け、結果検証後にだけ次世代へcommitする。
cursorや証明書はsession・generation・件数に結びつけ、失敗・容量変更・
別snapshot・順序外評価ではreuseを無効にして正準な再構築へ戻す。
cache hitがなくても意味は同じ、という契約を保つ。

計測hashと物理operatorを別々に版管理する。hashを省く高速経路を作る場合も、
完全な出力検証と破損注入による受理・拒否の一致を保つ。
arenaの寿命・初回page fault・Haskell側の遅延評価を計測条件に含める。
thread優先度やGC設定の調整は、後続のhitchまで含む同条件の比較で採否を決める。

Afterlightが実例として示すのは主に純粋な地形編集、増分描画、native資源管理。
この節の完全剛体解法やexact evaluatorを実装したゲームではない。
