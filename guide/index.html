庭の景色 · 夜

宝石を掘ると、
地形と所持品が変わる

宝石を掘ると、庭から宝石が消え、所持品が一つ増えて音が鳴ります。この処理を、状態の更新と音の再生に分けています。

まず、現在の状態と操作から、更新後の状態を計算します。描画と音声の処理は、その結果を受け取ります。状態を更新する関数が描画や音声の処理を呼ばないので、画面を開かずにゲームのルールをテストできます。描画方法を変えるときも、この関数は共通で使えます。

02 / TECHNIQUE

進行・時間・地形編集を
型と関数で表す

物語の進行は一つの型で表し、短い入力は次の更新まで保持します。地形の編集は、複数の操作をまとめて適用できるようにしています。

Garden.Types

物語の進行をJourneyで表す

Journeyに、覚醒から庭の再生までの段階を持たせます。飛行や帰還の状態をここから導くので、別々のフラグを揃え続ける必要がありません。

覚醒→夜の招来→飛翔解放→庭の再生

Garden/Types.hs ↗

data Journey = Awakening | NightInvited | Lightborne | GardenRenewed
  deriving (Eq, Ord, Read, Show)
Garden.Clock
60ticks / sec

ゲームの状態は、1回の更新（tick）で1/60秒進みます。描画だけを行うフレームでジャンプを押しても、入力を次のtickまで保持します。

描画の頻度とゲーム内の時間を分けて管理します。

処理が遅れたときは

経過時間を残し、一度に最大8tickずつ取り戻します。押した瞬間の入力は最初のtickに一度だけ渡し、マウスの移動量はtick群へ分けます。1秒の停止後にも60tick分が残ることを検査しています。

Garden.Change

地形の変更をChangeにまとめる

「ここに置く」「ここから取り去る」をChangeとして組み合わせます。同じセルへの操作は、後の操作が優先されます。

結果：このセルには何も残らない。

合成してから反映しても、順に反映しても同じ

apply (a <> b) garden
  == apply b (apply a garden)

Changeには、変更を合成するSemigroupと、何もしない変更を定めるMonoidのインスタンスがあります。保存時も、地形の差分をChangeで表します。

変更を表す型と、ほかの法則

Garden/Change.hs ↗

newtype Change = Change (Map Cell (Maybe Material)) deriving (Eq, Show)

place :: Cell -> Material -> Change

remove :: Cell -> Change

apply :: Change -> Map Cell Material -> Map Cell Material
apply mempty garden == garden
apply (between before after) before == after
Garden.Signal / Yampa

贈答のあと、光を徐々に弱める

贈答、飛翔、帰還のあとには、光が95tickかけて消える演出があります。この時間変化をYampaの信号関数で書いています。

Garden/Signal.hs ↗

lightEnvelope :: SF [Cue] Float

贈答のCue95tick後

SF [Cue] Floatは、出来事の列を受け取り、時間とともに変わる光の強さを返す型です。ゲームの進行はadvance、光の余韻はlightEnvelopeが受け持ちます。

Garden.Checkpoint

地形の差分とプレイヤーの状態を保存する

初期地形からの差分と、プレイヤーや在庫、物語の進行を保存します。光の余韻やGPU資源は保存せず、読み込み後に初期化し直します。

保存形式と実装

初期地形を識別する値（fingerprint）を照合し、異なる地形に差分を適用しようとした場合は読み込みを拒否します。保存形式はv4です。v3の検査用データを読み直す互換性検査もあります。

CPU側から測った描画の所要時間です。GPU単体の処理時間ではありません。

120FPSの上限に対応する、1フレームの時間。

測定した新版の3設定では、フレーム中央値はいずれも8.33msでした。120FPSを上限としているため、描画時間が短くなっても、そのぶんFPSが上がるとは限りません。

一方で、初期読み込みは3.43 → 5.31秒

新版高画質では、増えた頂点属性の生成と転送に時間がかかります。

  1. 01

    隠れた面を作らない。

    地形の内部に埋もれた面を省き、露出している面をメッシュにします。

  2. 02

    まとめて描く。

    8×8×8セルを1チャンクとして描画します。描画チャンクは4,461から1,498へ減りました。

  3. 03

    変わった範囲を作り直す。

    変更セルと周囲26セルにかかるチャンクを更新します。変更履歴と版番号を使い、描画を省略した間の編集も反映します。

  4. 04

    見えない地形を描かない。

    カメラから見える地形を判定し、描画対象を絞ります。影は別に判定し、画面外の地形が落とす影も描きます。

  5. 05

    Cとの受け渡しを減らす。

    C側の参照を再利用し、毎回の配列変換を省きます。転送後の不要な頂点リストも残さず、GCがたどるデータを減らします。

  6. 06

    効果に合わせて解像度を選ぶ。

    雲・接地陰影・ブルームには、解像度を下げたバッファを使います。UI解像度やゲームのtickは保ちます。

06 / CRAFT

操作感と遊びの流れを
確かめる

四つの浮島でも、庭と同じように採掘や建築ができます。帰還後も建てたものが残ることや、物語の進行に応じて飛行が使えることを確認します。

ジャンプ入力に猶予を持たせる

着地の少し前に押したジャンプ入力を保持し、着地時に使います。足場を離れた直後にも、短い間はジャンプできるようにしています。

ゲームを一時停止して構図を調整する

撮影カメラをゲームの状態と分けて管理しています。ゲームを一時停止したまま、光や影、雲の見え方を確かめ、構図、傾き、画角、露出を変えられます。

画面なしで物語から四島の建築までテストする

自動巡回ではゲームの入力を生成し、本番と同じadvanceを呼びます。贈答、救出、飛行、帰還を経て、四つの島で建築できるところまで確認します。

贈答→夜の救出→飛翔→帰還→四島で建築

Garden/Tour.hs ↗

tourInput :: World -> Input

Garden/Rules.hs ↗

描画や音声を起動せずに、ゲームのルールを検査できます。

素材の数量、セーブからの復元、地形の変更と描画更新の対応などは、生成したデータを使うテストでも確かめます。

テストで確かめていること

生成ケースは描画計画250、変更の法則200、衝突160、入力再実行120、描画更新範囲70の合計800件。具体例と、物語・四島の自動巡回も加えています。

型、生成テスト、自動巡回、実機の操作確認では、確かめられることが異なります。Haskell版はすべての不正状態を型で排除しておらず、全入力の正しさや、WindowsとWasmでの浮動小数計算のbit単位の一致までを保証するものではありません。

状態更新とIOの分け方、入力や保存の扱い、テストの方法を、ほかのゲームでも参照できる実装指針にまとめています。

実装と、ほかの作品へ持ち出す知見

公開版には、複数作品から抽出したAI向けの実装指針fp-gamedevとhaskell-excellenceを同梱しています。そこに含まれるすべての技術を、この一作で実証したという扱いはしていません。

IDRIS 2で試していること素材の消費数と残量の関係を型で確かめる
3 = 1 + 2使う前の在庫 = 消費数 + 残量

別に作っているIdris 2版では、この関係の証拠と、実際に次の世界へ組み込む在庫を、一つの戻り値に結び付けています。在庫不足なら、成功結果を返しません。

本番の配置・贈答・工作がこの関数を使います。物語の段階に依存するプレイヤーの型や、特定の世界と住人に結び付く救出許可もあります。証拠用の値は実行時に消去されます。

選んだ性質を、その計算結果に結び付ける実験です。全ゲームや浮動小数、C・GPUの資源管理までを形式証明したものではありません。

Idris 2版の記述は、開発中のソースと検証記録に基づきます。

ルールと描画を
分けて開発する

Afterlightでは、採掘や贈答による状態の変化を純粋関数で計算し、その結果を描画・音声・保存の処理へ渡しています。

この構成なら、描画を高速化したりブラウザ版を作ったりするときも、同じ関数でゲームを動かせます。ルールを変更したときは、画面を開かずにテストできます。

型と関数の役割を確かめながら、必要な実装を公開ソースで読んでみてください。
